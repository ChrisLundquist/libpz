# libpz Future-Pipelines Roadmap

**Date:** 2026-06-09  
**Method:** 17-agent research workflow (8 families researched + adversarially vetted + synthesized). ~1.46M tokens, 523 tool uses. Anchored on the parallel-decode thesis; seeded with the M5 dead-ends. Load-bearing code claims re-verified against the tree.

> This supersedes the gzip-era [pareto-competitiveness](2026-02-22-pareto-competitiveness.md) framing: the bar is now zstd, and the measured finding is that pz is *not* single-thread Pareto-optimal — its only defensible corner is **maximum ratio that also decodes block/segment-parallel**.

---

*Ranked by fit to the parallel-decode thesis. Synthesized from 8 vetted research assessments, with load-bearing code claims re-verified against the tree (June 2026).*

---

## 1. Strategic synthesis

pz's only structurally defensible Pareto corner is **maximum ratio that *also* decodes block/segment-parallel** — every codec in the high-ratio tier (LZMA, brotli-11, PPMd, bzip3, zpaq, cmix) decodes single-threaded, so any pipeline that reaches their ratio while riding libpz's existing per-block decode fan-out occupies a (ratio, aggregate-decode-throughput) point nothing mainstream holds. Against that thesis, two bets dominate, and they are deliberately ordered by *risk-adjusted* return, not by ratio ceiling. The strongest near-term bet is **BWT + a bzip3-style order-1 context-mixing range coder** (`pz bw` is already block-parallel; swapping its MTF→RLE→FSE tail for a ~70-line binary CM coder is a *medium*, drop-in change that targets ~25-27% on Silesia — beating zstd-9 and roughly tying xz — while keeping block-parallel decode). It is the highest ratio-per-engineering-dollar candidate because the suffix-sort transform, container, and decode scheduler already exist and need zero change. Co-leading, and the **best pure-risk-reward play**, is the **cross-block immutable dictionary / LDM** family: it is the rare high-ratio lever that costs *nothing* to parallel decode (a dictionary is immutable "past" that all decode workers reference read-only — verified: `decompress_block` carries no history argument), and its cheap spike either banks a free ratio widen on Silesia's structured files or redirects to the uncontested small/versioned-data regime (10%–5× wins nothing else combines with parallel decode). Everything else is either a slower, riskier path to the same corner (LZMA-class range coder, ROLZ, full CM) or a narrow per-file win (numeric transforms). The decisive theme: **prefer the candidate that reuses the most existing block-parallel machinery and de-risks with an encode-side or single-block spike**, because pz has already shipped two silent BWT-corruption bugs and a from-scratch carry-safe range coder is the single most corruption-prone primitive on the table.

## 3. Top-3 spikes

### #1 — BWT + order-1 CM range coder

**Spike (1-2 days, no wire format, no libsais, no LZP):** Port the ~70-line bzip3 model verbatim into a standalone `src/bwt_cm.rs` — `C0[256]`, `C1[256][256]`, `C2[512][17]`, the `((p0+p1)*7 + 2*p2)>>4` mix + APM + shift updates over a binary range coder. Feed it the **raw BWT bytes** from the existing `bwt::encode` output for a *single* 512KB-1MB block (no MTF, no zrle). On **dickens** (text, expect big win), **x-ray** (binary — validates there is no byte-255 fallback cliff, since `src/zrle.rs:43` cripples today's `bw` on any block with byte 255), and a Silesia blob slice, measure (a) compressed size vs the current MTF→RLE→FSE tail and (b) single-thread decode MB/s.

**Expected payoff:** CM size ≤ 0.90× of current `bw` on dickens at <512KB blocks; decode ≥ ~20 MB/s/core. That single ratio-delta-at-fixed-block-size number settles whether order-1 CM justifies the ~3× per-core decode hit *before* touching libsais, LZP, block-size tuning, or the wire format. If it passes, `pz bw` becomes a ~25-27% codec that decodes block-parallel — a frontier point in a tier where xz/bzip3/ppmd/zpaq are all single-threaded.

**Main risk:** Per-core decode is a hard ~3× regression vs today's `bw` FSE tail (a bit-serial range coder with 3-4 dependent table loads/bit is a *worse* latency-bound chain than rANS, and the M5 entropy wall offers no SIMD rescue). It is sellable **only** as a high-ratio parallel tier, never a default or speed competitor. Correctness is the real cost: two prior silent BWT-corruption bugs mean the carry-safe range coder needs aggressive round-trip fuzzing. The block-size knob has a narrow sweet spot — large blocks for ratio collapse parallelism on small files.

### #2 — Cross-block immutable dictionary + LDM

**Spike (~1 day, no new wire format):** In `lzseq` `encode_with_config`, build the `HashChainFinder` over a **16-32 MiB sliding prefix** (dict = all preceding bytes) instead of per-1MiB-block, while still slicing output into independent blocks; on decode, pre-prime each block's output buffer with the needed prefix. Measure **only**: (1) Silesia blob ratio delta *and the per-file table* (expect the win concentrated in xml/nci/dickens + version-duplicated slices, ~nothing on already-local text), and (2) confirm decode stays block-parallel by holding the dict in one `Arc` with workers referencing it read-only — assert aggregate MB/s is flat.

**Expected payoff:** If the per-file table shows a clean multi-pp win on the long-range-redundant subset with decode throughput flat, the immutable-dict thesis is validated — pz moves from "loses to zstd-3 on ratio" to "~ties zstd-3 ratio while keeping the 2.4-2.7× parallel-decode edge." Verified structurally: `decompress_block(payload, pipeline, orig_len)` takes no history argument, so adding `&Arc<[u8]>` keeps every block independent (this is exactly how zstd dictionaries provably work).

**Main risk:** On the *Silesia blob* the win is modest (~1-1.5pp; the 1 MiB window already captured the big local-redundancy gains, per the documented 256KB→1MiB = -1.6pp). The genuinely large value (regime B: shared/trained-dict on versioned/small data) the headline benchmark *can't show*. Decision rule: if blob delta is <1pp everywhere, the window already captured it — pivot straight to regime B (trained-dict builder, separate product). Secondary: the per-block dict-priming memcpy is a real aggregate-throughput tax on the bandwidth-shared M5 — keep the dict to a few MiB.

### #3 — Numeric front-end (transpose + byte-plane + delta)

**Spike (~1 day, CPU-only, no detection):** In a scratch test, implement **only** forward+inverse 16-bit delta + zigzag + byte-plane split (hardcoded 2-byte stride) and a hardcoded 28-byte transpose. Run x-ray and sao bytes through it, feed the planes into pz's **existing** order-0 rANS/FSE encode, and verify (a) round-trip correctness and (b) compressed size: target **x-ray < 50%**, sao < 66%.

**Expected payoff:** An end-to-end-validated harness already hit **x-ray = 44.4% with a verified round-trip** (vs pz-lzf 76.8%, pz-bw 54.9%, zstd-19 ~60.5%, xz-9e ~53%, bzip2 ~47.8%) — pz goes from *worst-in-class to beating xz and bzip2* on its single worst file, while decoding block-parallel. That one number validates the whole family. Phase 2: wire as a `Pipeline` variant, route via the existing `--trial` selector (avoids fragile stride heuristics), add per-plane delta gating.

**Main risk:** Three framing errors in the research change the engineering: (1) pz has **no order-1 entropy coder**, so the headline "47.3% via split+order-1" is unreachable — the real lever is **delta** (the research treated delta as the *risky optional* stage; it is the load-bearing one). (2) There is **no within-block per-plane parallelism** (`decode_multistream` is serial); parallelism is block-level only, and x-ray/sao are small (~8-16 blocks), so quote aggregate at block granularity, not full-18-core. (3) **sao is a weak ~15pp win** where blanket delta *hurts* — not a co-headline; gate delta per-plane.

## 4. Park / reject

- **Full context-mixing pipeline (#6, no BWT)** — *park.* Highest ratio ceiling (~20-23%) but aggregate decode lands at only ~13-36 MB/s on 18 cores (verified per-core: ppmonstr 0.28 MB/s, mcm 1.7-2.9, lpaq ~0.3-1) — 40-100× below pz today and uncomfortably close to plzip/xz-T. A from-scratch range coder + fixed-point mixer is a large, silent-corruption-prone bet for a narrow, core-count-conditional corner. **Pursue only the binary-range-coder-on-literals sub-spike if #1's coder proves out** — never the full chain first.
- **LZMA-class range coder (#4)** — *park behind #1.* Same range-coder primitive, but with bit-exact coupling between coder, context-literal model, and price-parse that "took LZMA years to tune" (*huge* cost), and it fights the M5 entropy wall head-on for only ~1pp over a byte-aligned alternative. If a range coder is built at all, build it inside #1 (smaller surface) first. The cheap Stage-0 insight (order-1 context-bucketed literals into *existing* rANS) is worth running, but it points at a Brotli-style path, not the LZMA range coder.
- **ROLZ (#5)** — *park.* Real ratio lever (~28-29% blob), but the parallel-friendly variant (static-table, orz-style) only *ties zstd-19* — the "beats brotli ~27%" headline requires CM literal coders that are **latency-bound dead-ends**. Cache-missing per-token bucket gather caps aggregate scaling (~1 GB/s, ties zstd not beats). Gated entirely on an unmeasured index-entropy spike. Lower priority than #1/#2 which reuse more and de-risk cheaper.
- **Repeat-offset-aware optimal parse (#7)** — *reject as a Pareto move.* Rep-state buys ~0.1pp on text, doesn't *extend* parallel decode (every LzSeq variant already has it), and `-O` currently aliases `--lazy` (the parser truncates offsets — `Match.offset` is `u16` at `src/lz77/mod.rs:48`). The valuable levers it surfaces (make lazy ≥ greedy; un-alias `-O` with u32 emit + real-entropy cost model; btultra2 two-pass) are separate parse-program work, not rep-state.
- **Parallel/segment entropy decode (#8)** — *reject the ambitious form; do the one-liner.* The M5's own 2026-06-09 measurement shows 4-way FSE interleave = **1.15×** ("the wide OoO engine already hides single-stream latency") — the inverse of this family's premise. 8-way scalar rANS *degrades* in every published benchmark (collides with the documented no-fast-gather wall). **Do** the free cleanup: route the `Lzf` default from single-state `fse::decode` to the existing 4-way `fse_decode_interleaved` (~1.15×, ratio-neutral, one line). **Do not** build an N=6 FSE substream stage.
- **Anything GPU (entropy, match-finding, Huffman)** — *reject, per dead-ends.* All candidates above are pure-CPU scalar by design; none re-trigger the GPU traps. ROLZ's bucket gather and the CM hash-table thrash are exactly the recency-dependent patterns that killed GPU atomics — confirming these stay CPU-only.

## 5. Proposed sequence

The sequence front-loads the two cheapest, highest-confidence spikes whose **outcomes gate the expensive bets**, and banks free wins along the way.

1. **Free win, do immediately (1 line):** Route `Lzf` decode to the existing 4-way `fse_decode_interleaved` (~1.15× decode, ratio-neutral, zero new code/wire). Clears the only defensible part of family #8 off the board.

2. **SPIKE #2 first — Cross-block dictionary (~1 day, encode-side only).** Cheapest decisive experiment, no new wire format, *cannot* break decode parallelism (dict is read-only). **Unlocks:** either a near-free larger-window/LDM ratio widen on the Silesia blob (proceed to additive header + coarse LDM pre-matcher), *or* a clean redirect to the regime-B trained-dict product if the blob delta is <1pp. Run before #1 because it's lower-risk and its result is independent.

3. **SPIKE #3 in parallel — Numeric front-end (~1 day, CPU-only).** Independent of #2, already partially validated (x-ray 44.4% verified). **Unlocks:** per-file dominance on pz's worst class (sao/x-ray) via a `Pipeline` variant + `--trial` routing. Bank x-ray; treat sao as optional.

4. **SPIKE #1 — BWT + CM range coder (1-2 days, single block, standalone).** The big ratio bet, but gated to a single-block measurement first. **Unlocks (if it passes the ≤0.90× / ≥20 MB/s gate):** (a) the highest-ratio block-parallel tier libpz can hold (~25-27%, beats zstd-9), and (b) **a proven, fuzzed binary range coder** — the single primitive that every remaining high-ratio family (#4 LZMA-class, #6 full CM) depends on. This is why #1 is sequenced as the *gateway*: build the range coder once, in its smallest correctness surface (post-BWT bytes), and only then decide whether to extend it to context-literals (#4) or a full ICM-ISSE chain (#6).

5. **Decision gate after #1.** If the range coder lands clean: phase-2 #1 adds libsais (encode speed) + block-size sweep + LZP. *Then and only then* evaluate whether to spend the coder on the LZMA-class literal path (#4) — and only if a cheap order-1-literals-into-existing-rANS measurement shows >2-3pp on text. Park #5/#6 unless #1 reveals unexpected per-core decode headroom on this hardware.

**Net:** three medium spikes, two of which (#2, #3) are ~1-day and de-risk independently, plus one gateway spike (#1) that — if it pays off — both ships the strongest single ratio win *and* unlocks the entire range-coder family at the lowest possible correctness risk. Every step preserves block/segment-parallel decode; none touches a documented dead-end.

## Appendix: per-family assessments (8 families, research + adversarial vet)
### LZMA-class: range coder + context-modeled literals + optimal parse — **PROMISING** (cost: huge, confidence: high)
_An LZMA-class pipeline (adaptive binary range coder + match/prev-byte context-modeled literals + true price-based optimal parse) would close ~6-9pp of ratio to reach the brotli-11/lzma frontier (~24% on Silesia text, big wins on the binary worst-files), and because the range coder is serial only WITHIN a block while libpz already decodes blocks in parallel, it is the single best fit for the "max-ratio + parallel-decode" thesis — at the cost of dropping per-core decode from ~432 MB/s (rANS) to ~90-130 MB/s (LZMA-class), recovered only by block fan-out._
- **Expected Pareto position:** Honestly: a new frontier point that nothing mainstream occupies, but at a more modest ratio than claimed. Realistic landing on Silesia text at 1 MiB independent blocks: ~25-27% ratio (range-coder variant) or ~26-28% (Brotli-static-Huffman variant), at ~90-150 MB/s/core decode for the range coder (a ~3-4x per-core REGRESSION vs LzSeqR's 432) or ~350-400 MB/s/core for the Huffman variant. The defensible corner is AGGREGATE parallel decode: ~1.4-2 GB/s across the M5's cores at ~25% ratio, while lzma/xz/brotli/ppmd ALL decode single-threaded (xz parallel-decode is explicitly a 'future version'). So vs zstd: it LOSES to zstd-3/zstd-19 on per-core decode and on compress speed, but on the ratio-at-parallel-decode axis it sits between zstd-19 (27.9%) and zstd-22 (24.69%) while decoding ~1.5-2x faster in aggregate than zstd's single-threaded CLI — a corner zstd cannot reach without its own block-parallel decode. It is NOT single-thread Pareto-optimal and never will be. The win is strictly conditional on block fan-out, exactly as the proposal admits.
- **Parallel-decode verdict:** YES at block granularity — this is the one claim that holds up under maximum skepticism, and it is the whole reason the family is viable. Verified in pipeline/parallel.rs:371 (decompress_stream_parallel spawns one decode per block via thread::scope, non-overlapping output slices, zero hot-loop sync) and streaming.rs decompress_stream_parallel. Each ~1 MiB block self-describes (method + orig_len in the block table), resets coder/model/rep-state, and decodes serially. The serial-WITHIN-block property is real and unavoidable: an adaptive range coder's prob tables evolve per-bit, so there is genuinely no sub-block parallelism and Recoil's split-point trick is inapplicable (confirmed in recoil.rs — it relies on rANS state being recomputable, which adaptive context is not). The skeptical caveats that DON'T break it but shave the aggregate: (1) FIFO drain in parallel.rs serializes the straggler tail, no work-stealing; (2) M5's 6P+12E heterogeneity means E-cores decode the branchy loop much slower, so ~1.4 GB/s is more honest than ~2 GB/s; (3) smaller blocks for more parallelism directly trade away ratio (the ratio<->parallelism tension is real and the 1 MiB block is already near the floor where the model can warm up). Net: parallel decode is preserved at exactly libpz's existing scale and is the genuine strategic edge — but it must be benchmarked as aggregate; any single-thread decode benchmark will read as a 3-4x regression and look like a disaster.
- **Dead-end collisions:** Entropy-decode-is-at-a-hardware-wall (CLAUDE.md): an adaptive binary range coder is MORE latency-bound than rANS, not less. rANS 4-way interleave already only buys 1.15x and SSE2 rANS is 32% SLOWER than scalar on the M5's wide OoO core. A range coder cannot interleave N lanes at all (the prob tables evolve symbol-by-symbol), so it forfeits even that 1.15x. This dead-end does NOT kill the family, but it hard-caps per-core decode at ~90-150 MB/s and means the proposal's pure-range-coder variant is fighting the exact wall the codebase documents. The Brotli-style static-Huffman fork sidesteps it. CPU-Recoil-via-thread-scope-is-60x-too-slow / parallel entropy must ride BLOCK parallelism: this CONSTRAINS the design rather than killing it. Recoil's split-point trick (recoil.rs) explicitly depends on rANS state being recomputable with no adaptive context; an adaptive range coder has no cheap mid-stream resume point, so Recoil is inapplicable. The ONLY parallel-decode mechanism available is the V2 block container (pipeline/parallel.rs:371), which is exactly what the proposal proposes to use. Consistent, but it means parallelism granularity is fixed at the block, never sub-block. Greedy-parse-as-default-regresses-structured/record-data: the proposal's price-based optimal parse must beat lazy on ALL data classes, but CLAUDE.md documents that even --greedy regresses structured/record data and 'making lazy >= greedy everywhere is an open follow-up'. A mis-priced LZMA optimal parse risks the same regression on sao/x-ray record data where the proposal claims its biggest wins.
- **Vet rationale:** This is the highest-ratio-ceiling family on offer and the ONLY one whose serial-decode penalty is confined to within-block (where libpz already parallelizes across blocks), so it genuinely fits the 'max-ratio + parallel-decode' thesis better than any alternative. All external numbers verified against lzbench 2.0.1 (lzma-9 22.97%@93MB/s, brotli-11 23.78%@389, lzham 25.83%@309, ppmd8 24.18%@12 symmetric, zstd-22 24.69%@1073). The code-level claims hold: no range coder/context model exists anywhere (grep empty), the V2 block container fans out decode across cores, and Recoil cannot rescue an adaptive stream. I rate it PROMISING not PURSUE for three reasons: (1) the ratio claim is inflated — lzma's 22.97% is a 64 MiB-dictionary single-stream number, and libpz's 1 MiB independent blocks + per-block model reset realistically land at ~25-27%, comparable to zstd-22/lzham, a ~5-7pp gain not ~9pp; (2) the cost is genuinely huge and shatters the tokenize->streams->entropy abstraction (the range coder IS the entropy stage, so none of the FSE/rANS/SIMD infrastructure carries over) with bit-exact coupling between coder, context model, and price-based parse that 'took LZMA years to tune'; (3) the pure-range-coder variant fights the documented M5 entropy wall head-on (it is more latency-bound than rANS, which SIMD already made 32% worse) for only ~1pp over the Brotli-style context-literals + static-multi-table-Huffman fork that decodes ~4x faster per-core (389 vs 93) and reuses libpz's existing Huffman + byte-stream machinery. The decisive recommendation: run the proposal's Stage 0 spike FIRST — order-1 (prev-byte) context-bucketed literals fed into the EXISTING rANS/FSE, measuring ratio on Silesia text + x-ray/sao in hours with zero new coder. If context literals deliver >=2-3pp, build the BROTLI-style path (context literals + multi-table static Huffman as a new block type), NOT the LZMA range coder — it captures most of the ratio, stays byte-aligned (which the M5 wants), keeps per-core decode in the 350-400 MB/s class, and avoids the huge latency-bound hand-tuned-scalar-hot-loop liability. Reserve the full range coder only if the Brotli fork demonstrably leaves >1.5pp on the table AND aggregate decode stays above ~1.5 GB/s. Context-modeled literals are the real lever here; the adaptive binary range coder is an expensive, slow-decoding way to spend the last ~1pp on a machine explicitly hostile to it.
### ROLZ / LZP / context offset prediction — **PROMISING** (cost: large, confidence: high)
_Replace LzSeq's raw log2 offset-extra bits (~46% of compressed text) with a per-context offset bucket index (ROLZ): this reaches LZMA-class ratio (~27% on text vs today's 32%) and — because the serial bucket dependency is intra-block only — still rides libpz's existing 1 MiB block-parallel decode, landing on the exact "max-ratio + parallel-decode" Pareto corner the thesis targets._
- **Expected Pareto position:** Realistic libpz-compatible ROLZ (static-table FSE/rANS, no CM literal coder, 1 MiB block reset): ratio ~28-29% on the Silesia BLOB (vs pz-today 32.2%, zstd-3 31.2%, zstd-9 27.9%, zstd-19 24.9%) — so it lands BETWEEN zstd-9 and zstd-3 on ratio at the blob level, with text members reaching ~zstd-19 territory and binary/numeric members (sao, x-ray, mozilla) gaining ~nothing. Per-core decode ~150-180 MB/s (orz-class) = ~2.5-3x SLOWER than today's lzseqr 432 and ~8x slower than zstd's per-core. Aggregate parallel decode ~1000-1200 MB/s (sub-8.5x scaling due to cache-missing gather) = roughly ties zstd's single-thread CLI decode (1350-1500), not the clean 'match' the proposal claims. Encode WORSE than today (bucket-constrained search, orz ~30 MB/s class), widening the already-losing compress axis. NET PARETO MOVE: a genuine new frontier point = 'zstd-9-class ratio at ~1 GB/s aggregate-parallel decode' that no mainstream high-ratio codec holds (lzma/brotli-11/rzm all decode single-threaded at 5-50 MB/s). That IS a defensible corner, but it is 'beats zstd-9 on ratio while decoding in parallel,' NOT the pitched 'LZMA-class ~27% beating brotli.' Marginal-to-real win, gated entirely on the index-entropy spike.
- **Parallel-decode verdict:** Skeptical but ultimately YES for the FULL-ROLZ-on-static-tables variant — this is the proposal's strongest and best-grounded claim, and I verified it against the code. The decode workers (streaming.rs:683-699) are fully block-independent: each spawns a loop that pulls one (idx, block_data, orig_len) off an Arc<Mutex<rx>> work queue and calls decompress_block with ZERO cross-block shared mutable state; reordering happens only at the writer via a BTreeMap. Buckets reset at block start, so ROLZ's serial bucket dependency is strictly intra-block and inherits this inter-block parallelism with no scheduler change — exactly as claimed. Two honest deductions from the pitch: (1) The serial dependency is NOT removable intra-block — Recoil-style bitstream splitting does not apply because ROLZ's serial chain is the bucket gather, not the entropy stream. So a ROLZ block decodes single-threaded internally; parallelism is ONLY the existing 1 MiB block granularity. Small inputs (<~2-4 MiB) and single-block streams get NO parallel rescue and pay the full ~3x per-core penalty — ROLZ must be positioned as a bulk/max-ratio pipeline, never a low-latency or small-payload default. (2) The aggregate ceiling is lower than pitched: the per-token random gather into 512x4094-entry rings is cache-missing, so under N-core load it contends on shared LLC/memory bandwidth in a way LzSeq's register-resident rep-cache does not — aggregate scaling will be sub-8.5x (est 6-7x), landing ~1000-1200 MB/s, a tie-with-zstd rather than a clean win. The block/segment-parallel decode IS preserved at libpz's scale, but the edge is 'roughly ties zstd aggregate decode while delivering much better ratio,' which is still the thesis corner — just thinner than advertised. The CM-literal ROLZ variants (rzm/TarsaLZP) do NOT preserve it and must be excluded.
- **Dead-end collisions:** NOT GPU-blocked: the proposal correctly keeps ROLZ on CPU. The bucket gather is recency/order-dependent — exactly the pattern that killed GPU hash tables here (atomics lose recency -> 6% match quality). So it does not RE-trigger that dead-end, but it confirms ROLZ can never be GPU-accelerated on this hardware. Encode and decode are both CPU-only. Brushes the entropy-latency wall but does NOT cross it IF kept on static-table FSE/rANS like orz's Huffman. The fatal version is ROLZ+context-mixing-arithmetic (rzm/TarsaLZP), whose 24.4%/24.8% ratios are the headline numbers but whose decoders are 81-2000 ns/b (5-12 MB/s, symmetric) — that is the 'CPU Recoil/adaptive coder is latency-bound' dead-end. The proposal's own 'keep it on FSE/rANS, not a slow adaptive coder' caveat is the load-bearing guardrail; without it this collapses into a known dead-end. Does NOT conflict with the ParlZ dead-end: ParlZ failed because it parallelized the PARSE (forward-max-propagation lost 37.6% ratio). ROLZ keeps serial CPU parsing and only parallelizes decode across existing blocks — the explicitly-endorsed 'hybrid serial-parse' architecture, not parallel parse. Does NOT conflict with the SIMD-rANS/4-way-interleave wall: ROLZ's decode bottleneck is the bucket gather, not the entropy stream, so it neither needs nor benefits from intra-block entropy SIMD — it sidesteps that wall rather than fighting it. Aggravates the known compress-side weakness (per-core ~50-70 MB/s, 6-9x behind zstd): bucket-constrained match search (orz ~30 MB/s encode on enwik8) makes the already-losing compress axis worse. Not a new dead-end, but it widens the axis where libpz is least competitive.
- **Vet rationale:** This is the most credible ratio lever surveyed for libpz, and it genuinely targets the thesis corner (max ratio + parallel decode), so it clears 'reject' and 'marginal.' It does not reach 'pursue' because the headline is mis-calibrated on two load-bearing points I verified against independent sources and the code: (1) the ~27%/beats-brotli ratio comes from CM/PPM literal coders that are the explicitly-banned latency-bound decoders; the parallel-friendly ROLZ (orz, static Huffman) ties zstd-19, not beats brotli — so the realistic libpz target is zstd-9-class blob ratio, a real but more modest win; and (2) the 'per-block mixed pipeline, additive' framing is wrong for the CLI streaming path (single Pipeline tag in header[3]), though it remains additive as a new whole-stream tag. The parallel-decode thesis itself holds structurally (workers are fully block-independent, buckets reset per block), but the aggregate throughput will be sub-8.5x due to the cache-missing per-token gather, landing at a tie-with-zstd rather than a clean win. The decisive uncertainty is the actual bucket-INDEX entropy (1 vs 1.5-2 bytes) and bucket hit-rate (>90%?), which nobody has measured on this data. VERDICT JUSTIFICATION FOR 'promising': pursue the proposal's exact recommended spike — encode-side-only ROLZ index simulation over existing Vec<LzToken> per 1 MiB block, FSE/rANS the index stream, compare to the measured offset cost, and measure index entropy + bucket hit-rate EXPLICITLY (do not assume 1 byte). Decision rule: index <=60% of current offset cost AND hit-rate >90% -> proceed to full RolzEncoder + new RolzR pipeline tag (large cost, ~zstd-9-blob / ~zstd-19-text ratio, ~1 GB/s aggregate decode, slower encode, positioned as max-ratio-not-low-latency). If index >1.7 bytes or hit-rate <85% -> drop to ROLZ-lite (brotli 4-entry distance cache + adjust codes in RepeatOffsets, ~2 days, free ~0.5-1.5pp structured-data win, zero decode penalty). Keep it CPU; never couple it to a context-mixing arithmetic coder; validate ratio at 1 MiB AND 4 MiB blocks to bound the block-reset loss; fuzz cross-block for byte-identical bucket state (same silent-corruption class as the two fixed bbw bugs).
### BWT improvements: faster suffix sort + BWT+CM second stage — **PROMISING** (cost: medium, confidence: high)
_Replace pz bw's MTF→RLE→FSE tail with a bzip3-style binary range coder mixing order-0+two order-1 contexts (plus libsais for the suffix sort and larger blocks), turning pz bw into a 22-24%-ratio codec that still decodes block-parallel across all cores — the single most defensible Pareto corner libpz can occupy, since every codec in that ratio tier (xz, bsc, bzip3, ppmd, zpaq) decodes single-threaded._
- **Expected Pareto position:** A genuinely NEW Pareto point libpz can hold, but smaller and slower than the proposal paints. Honest landing: ~25-27% ratio (512KB-1MB blocks) at ~200-300 MB/s AGGREGATE parallel decode on the M5 Max. That is a frontier corner nothing mainstream occupies: every codec in the 22-27% tier (xz/lzma ~50-100, bsc, bzip3 single-file, ppmd, brotli-11, zpaq) decodes SINGLE-THREADED at 20-200 MB/s, so a 200-300 MB/s parallel decode at ~26% is uncontested. BUT it is NOT single-thread Pareto-optimal: per-core ~23 MiB/s decode is ~3x SLOWER than today's pz bw FSE (~74 MB/s/core) and ~60x slower than zstd huff0 — so on a 1-2 core consumer it is a hard regression. Versus zstd: still loses the compress axis utterly (zstd -T0 2.8-5.9 GB/s vs BwCm ~150-200 MB/s aggregate encode). The play is a high-RATIO parallel-decode tier, sold explicitly as such, NOT a default and NOT a speed competitor. It does NOT meaningfully fix the worst-files (sao 73.8%, x-ray 54.9%): removing the zrle-255 cliff + order-1 model buys a few pp (x-ray ~48-50%), as the proposal honestly states — those need a delta/structure transform, out of scope.
- **Parallel-decode verdict:** YES — it genuinely preserves block-parallel decode at libpz's scale, and this is verified in code, not assumed. The CLI decode path spawns num_threads workers each independently calling decompress_block(pipeline, orig_len) on a framed block (src/streaming.rs:683-698); the in-memory path does the same via thread::scope (src/pipeline/parallel.rs:371-384). A BwCm block is independently decodable (carries its own primary_index + CM bitstream), so it slots in with ZERO new parallel infrastructure — exactly like Bw does at 512 KiB blocks today. This is the family's whole reason to exist and it holds up. The skeptical caveats are about MAGNITUDE, not existence: (1) the granularity tension is real and asymmetric — chasing bzip3's ratio needs MB-to-tens-of-MB blocks, and at, say, 8 MiB blocks a 202 MB Silesia blob is only ~25 blocks, so you saturate 18 cores but a SMALL file (<a few MB) collapses to 1-3 blocks = near-single-threaded decode at 23 MiB/s, which is BRUTAL for the small/low-core case. (2) Aggregate throughput is gated by the heterogeneous P/E cores AND shared-memory contention from 18 simultaneous cache-random inverse-BWT LF-walks, so the real aggregate is ~200-300 MB/s, below the claimed 400 and well below today's bw ~1120 MB/s aggregate. (3) The parallelism is coarse-grained (block) only — there is NO intra-block parallel decode for a serial range coder (and per the M5 latency dead-ends, none is achievable), so the operating point is rigidly (block_size, ratio, core_count)-coupled and must be measured, not assumed. Net: parallel decode survives; it is the only thing that makes the family defensible; but the (block-size up for ratio) vs (block-size down for parallelism + small-file latency) knob is a genuine tradeoff with a narrow sweet spot, not a free win.
- **Dead-end collisions:** NONE that kill it. The CM coder is pure scalar-integer CPU, so it sidesteps every GPU dead-end (GPU entropy 0.5-0.8x, GPU Huffman, GPU hash tables) and the SSE2-rANS dead-end entirely — there is no SIMD/GPU path proposed. The 'GPU coordinator serialized entropy at 28 MiB/s in the parallel scheduler' dead-end does NOT apply: a CPU-only BwCm pipeline skips the webgpu offload branch (streaming.rs:369-401 is gated on webgpu_engine + LZ dispatch), so each block compresses/decodes on its own worker exactly like Bw today. Verified in streaming.rs:360-408 (encode) and :683-698 (decode). The 'window-capped suffix sort breaks BWT invertibility (FWST 433% expansion)' dead-end does NOT apply — libsais is a FULL suffix sort, not window-capped. This is the correct, structural choice the dead-end demands. PARTIAL REINFORCEMENT (not a block, but a warning the proposal under-weights): the M5 'FSE/rANS decode is latency-bound; 4-way interleave buys only 1.15x; SIMD rANS is 32% SLOWER than scalar' finding directly predicts the CM coder's per-core ceiling. A bit-serial binary range coder with 3-4 dependent table loads per bit is a WORSE latency-bound chain than rANS, and the same proven wall applies: no SIMD/ILP rescue exists. The proposal states this but frames it as a tolerable constant; on this exact hardware it is a hard floor.
- **Vet rationale:** All load-bearing claims verified. CODE (read directly): bw path = BWT->MTF->RLE/zrle->FSE (blocks.rs:244-294); CM coder is a clean drop-in for the tail behind a new Pipeline ID with no container change; encode AND decode are block-parallel via thread::scope with NO GPU-coordinator on a CPU-only pipeline (streaming.rs:360-408, 683-698; parallel.rs:371-384); zrle FALLS BACK to legacy rle on any block containing byte 255 (zrle.rs:43) — so today's bw is crippled on binary data and a CM coder removes that cliff; BWT uses SA-IS over the doubled string with a primary-index convention libsais must match (bwt/mod.rs:43-56); NO binary range coder exists to reuse (recoil.rs is rANS metadata). EXTERNAL (verified): bzip3 22.3% Silesia at large blocks; bzip3 README states ~17 MiB/s comp / ~23 MiB/s decomp PER THREAD verbatim and 16 MiB default block, ratio rises with block size; libsais ~82/121 MB/s 1T/MT, ~2.1x libdivsufsort. HARDWARE (verified sysctl): 6 P + 12 E cores, NOT 18 uniform — this is the proposal's biggest math error and discounts the aggregate-decode claim from ~400 to ~200-300 MB/s. VERDICT = promising (not pursue): the architecture fit and the parallel-decode thesis are real and uniquely defensible for libpz, but (a) the per-core decode is a hard ~3x regression vs today's bw and a 60x gap vs zstd, sellable ONLY as a high-ratio parallel tier; (b) the ratio (~25-27%) and aggregate decode (~200-300 MB/s) are both meaningfully worse than the proposal's headline; (c) the block-size knob has a narrow sweet spot and punishes small/low-core inputs. The proposal's own recommended spike is exactly right: build ONLY the bzip3-style CM coder, bolt it onto existing bwt::encode output for ONE 512KB block, and measure compressed-size-delta-vs-FSE-tail and decode-MB/s/core on dickens + x-ray BEFORE touching libsais/LZP/block-size/wire-format. That single ratio-delta-at-fixed-block-size number settles whether the order-1 CM justifies the ~3x decode-speed hit. Do the spike; gate everything else on it. Medium cost is fair (coder is small; the cost is correctness/fuzz testing given two prior silent BWT corruption bugs).
### Structured/numeric transforms for the worst files — **PROMISING** (cost: medium, confidence: high)
_A cheap, embarrassingly-parallel "numeric front-end" — record-stride transpose + byte-plane shuffle + conditional delta — feeding pz's existing per-stream order-1 rANS/FSE backend cuts x-ray ~70%→47% and sao ~74%→63%, landing exactly on pz's defensible corner (max-ratio AND block-parallel decode) on data where every high-ratio competitor decodes single-threaded._
- **Expected Pareto position:** x-ray: a genuine new frontier point. delta16+zigzag+split through pz's real order-0 FSE = 44.4% (verified round-trip), vs measured pz-lzf 76.8%, pz-bw 54.9%, zstd-19 ~60.5%, xz-9e ~53%, bzip2 ~47.8%. So pz would go from worst-in-class to BEATING xz and bzip2 on x-ray while decoding block-parallel (entropy-bound ~461 MB/s/core x ~8 blocks) where xz/bzip2 decode single-threaded. This is exactly libpz's defensible corner: max-ratio-on-numeric AND parallel decode. sao: real but modest, ~79.9%->~65% (transpose+per-column BW), beating zstd-19 (~69%) but backend-limited and unspectacular; not a frontier-defining win. Net Silesia-blob impact is small (x-ray+sao are 15.7MB of 202MB), so this does NOT move the headline blob ratio meaningfully (~ -0.5pp at most) — its value is per-file dominance on numeric data and a defensible story, not blob-ratio. Zero regression on text (transforms gate off via detection/trial; no record structure to trigger them).
- **Parallel-decode verdict:** Preserved, but more modest than advertised. The inverse transform is pure memory shuffle: I measured merge+unzigzag+prefix-sum delta at 4295 MB/s/core vs entropy decode 461 MB/s/core — ~9x cheaper, adding ~10% decode tax and, crucially, NO new latency-bound serial dependency (unlike LZ match-copy chains or BWT inverse-LF). Decode stays entropy-bound and rides the existing block-parallel decode (one thread per 1MiB block) exactly like the LZ pipelines. BUT two of the proposal's parallelism claims are false in this codebase: (1) there is NO within-block per-plane parallelism — decode_multistream is serial, so '2-28 planes on N cores' is fiction; parallelism is block-level only. (2) The target files are SMALL: x-ray 8.5MB = ~8 LZ-blocks (or ~16 bw-blocks), sao 7.25MB = ~7/~14 blocks, so realized decode width is ~8-16 cores, not the implied full-18-core 7 GB/s. The thesis still holds — this codec decodes block-parallel while xz/bzip2/brotli decode strictly single-threaded — but the 'extra free within-block parallelism' selling point evaporates and the aggregate-throughput numbers should be quoted at block granularity for these specific files. ndzip's published 'random-access-point parallel decompression' is accurate prior art that the FAMILY is natively parallel; it just maps onto libpz at block, not plane, granularity.
- **Dead-end collisions:** None directly. It is the opposite of every listed dead-end: pure CPU index-math, no GPU (avoids GPU-entropy/GPU-match/GPU-Huffman traps), no per-decode threads (avoids the 60x Recoil std::thread trap since it rides block parallelism + the existing serial multistream decode), no suffix-sort change (avoids the window-capped BWT 433% trap), no parse-conflict heuristic (avoids the ParlZ 37.6% trap). The ONE soft collision: the family's ratio case leans on per-stream entropy quality, and the dead-end list plus my code read confirm pz entropy is order-0 latency-bound at ~461 MB/s/core with no order-1 model and SIMD rANS disabled, so the proposal's order-1-dependent numbers (x-ray 47.3% via 'split+order-1') cannot be reached by the split alone.
- **Vet rationale:** I validated the core claim end-to-end against libpz's REAL code, not an entropy sim: built a harness linking pz's actual fse::encode_best/rans::encode/bwt path and ran the transforms on the real Silesia x-ray and sao. x-ray 16-bit delta+zigzag+split = 44.4% with a VERIFIED round-trip (ROUND TRIP: OK), beating pz-bw, xz, and bzip2 — a real, defensible, block-parallel-decoding win on libpz's single worst file class. That alone justifies a 'promising' verdict and a 1-day CPU spike. I downgrade from 'pursue' to 'promising' because the proposal's framing has three substantive errors that change the engineering, all confirmed by reading the code: (1) pz has NO order-1 entropy coder, so the headline 47.3%-via-split is unreachable and the real win is delta (the proposal treats delta as the risky optional stage); (2) there are NO per-block mixed pipelines and NO within-block per-plane parallelism — both decode paths apply one header pipeline and decode_multistream is serial, so the 'zero container change mixed-pipeline' and 'N planes on N cores' selling points are wrong, though a whole-file NumXform variant works cleanly; (3) sao is a weak, backend-limited ~15pp win where delta HURTS, not the co-headline. The spike should be: hardcoded 16-bit delta+zigzag+split for x-ray feeding existing order-0 FSE/rANS (target <50% — I already hit 44.4%), wire as Pipeline id 13, route via the existing --trial selector to avoid fragile stride heuristics, and route the sao transposed stream through the existing BW path (not rANS) if sao is pursued at all. Detection/auto-select and per-plane delta gating are phase 2. Cost is medium (new ~300-500 LoC transform + detection + enum/dispatch wiring + tests), not small, because the order-0 reality means delta/zigzag/elem-width handling and conservative detection are required for the win, not optional polish.
### Cross-block dictionary & long-range matching — **PROMISING** (cost: medium, confidence: high)
_Recover the cross-block context that block-independent compression throws away by priming each block's match window with an immutable shared dictionary (front-loaded ref block + optional trained/LDM dictionary) that decodes read-only — uniquely, this regains ratio with ZERO cost to libpz's block-parallel decode, because a dictionary is just immutable "past" that all decode workers reference concurrently._
- **Expected Pareto position:** Two distinct landings, and only one is on the stated benchmark. (A) Silesia-as-one-blob (the brief's benchmark): realistically lzseqr 32.2% → ~30.5-31.5% from a larger window + a coarse LDM pass, with the win concentrated in xml/nci/the version-redundant slices and ~zero on already-local text. That moves pz from 'loses to zstd-3 on ratio' to '~ties zstd-3 ratio (31.2%) while keeping the 2.4-2.7x parallel-decode edge' — a genuine, defensible Pareto improvement at the lzseqr operating point, but NOT a leap to zstd-19/lzma territory. (B) Off the Silesia blob, on small/versioned/repeated-context corpora with a shared dict (DB pages, RPC payloads, log lines, versioned assets): 10%-to-5x wins that NOTHING else combines with parallel decode — this is the family's actual killer regime and a frontier point mainstream codecs (which all decode serially) don't hold. Net: a solid frontier-widener at pz's existing operating point, plus a new uncontested corner in regime (B); not a new ratio class on the headline blob.
- **Parallel-decode verdict:** Holds up to scrutiny — this is the strongest part of the proposal and the reason it clears the thesis bar. I verified it three ways: (1) zstd's own format spec (fetched) states the dictionary 'act[s] as a past in front of data... referenced in sequence commands' and 'each frame with a matching Dictionary_ID can independently use the same dictionary — no frame must be decoded before another.' That is exactly decode-order-independence. (2) libpz's parallel decoder already matches this shape: `decompress_block`/`decompress_stream_parallel` carry NO cross-block history; blocks are dispatched to workers via a channel and reordered by index. A read-only `Arc<[u8]>` dict shared across workers preserves that 100%. (3) The reconstruction loops (lzseq/mod.rs:1050, lz_token.rs:165, demux.rs:264) validate `offset <= output.len()`, which works correctly when output is pre-primed with the dict — no semantic change to the back-reference resolution. The ONE genuine threat the proposal correctly identifies and rules out: a rolling inter-block history (block N referencing block N-1's live output) would serialize decode and destroy the entire edge — but the immutable front-loaded-dict discipline structurally avoids it, and is enforceable because the dict is a separate header section materialized once before dispatch. Skeptic's residual caveat: AGGREGATE throughput (not independence) can dip from the per-block dict-priming memcpy on a bandwidth-shared M5 when the dict is large relative to the block; keep the dict to a few MiB and this stays negligible. Block COUNT also stays >> core count (211MB / few-MiB blocks = dozens of blocks vs 18 cores), so saturation is fine. Verdict: parallel decode is genuinely preserved — the unicorn property is real.
- **Vet rationale:** Pursue the cheap, decisive form; defer the expensive form. The family is the rare high-ratio lever that adds NOTHING to libpz's proven dead-end pile: it's pure CPU LZ parse + larger window + read-only history priming — zero GPU entropy, zero GPU match-finding, zero GPU Huffman, zero suffix-sort, no per-decode threads (it rides the EXISTING block parallelism, exactly what the brief demands). The thesis (block/segment-parallel decode at libpz's scale) is not just plausibly preserved — it is how zstd dictionaries provably work, and it drops onto `decompress_block`'s history-free signature with one shared Arc. Architecture fit is excellent and largely wire-compatible (LzSeq offsets are already u32; only an additive header field is needed). The honest ceiling: on the stated Silesia-blob benchmark the win is modest (~1-1.5pp, concentrated in structured/long-range-redundant files), enough to TIE zstd-3 ratio while keeping pz's 2.4-2.7x decode edge — a real Pareto widen, not a leap; the lrzip evidence the proposal itself cites shows the long-range pass alone (sans an LZMA/zpaq backend pz doesn't have) is worth only a few percent. The genuinely large value is regime (B) — shared/trained-dict on small/versioned data — which the headline benchmark can't even show. I dock it from 'pursue' to 'promising' for two reasons the proposal underweights: (1) the per-block dict-priming memcpy is a real aggregate-throughput tax it dismisses as negligible, and (2) the full product (LDM + container dict-block type + COVER/fastcover trainer + 6-pipeline round-trip tests) is LARGE, not medium — only the recommended spike is medium. Recommendation: run exactly their spike (whole-blob/sliding-prefix HashChainFinder feeding the existing per-block slice, decode with one Arc dict), and gate on the PER-FILE delta table, not the blob aggregate. If xml/nci/dickens show a clean multi-pp win with decode MB/s flat, proceed to the larger-window variant (nearly free) and a coarse LDM pre-matcher, and treat the trained-dict builder as a separate regime-(B) product. If the blob delta is <1pp everywhere, the 1 MiB window already captured it — pivot straight to regime (B). Either branch lands a defensible frontier point; neither collides with a known dead-end.
### Context-mixing & PPM entropy — **MARGINAL** (cost: large, confidence: high)
_Block-parallel context mixing (the ZPAQ/mcm architecture) is the single best on-thesis family for libpz: it reaches LZMA-beating ratio (zpaq -m5 = 18.5% on Silesia vs pz's 32.2%) while decoding independently per block — but it requires a brand-new binary range coder, and per-core decode lands at a brutal ~1-10 MB/s, so the entire bet is "win on aggregate parallel decode at a ratio nothing parallel-decodable holds."_
- **Expected Pareto position:** Two distinct points. (1) Full CM/PPM block pipeline: ratio ~20-23% on Silesia (after the 1 MiB block-reset penalty, NOT the 18.5% whole-file figure), aggregate decode ~13-36 MB/s on 18 cores (PPMd-fast ~20, lpaq-class ~13, mcm-class ~36) vs pz lzseqr's current 3690 MB/s aggregate at 32.2% and zstd-19's ~1500 MB/s single-thread at 24.9%. This lands ~4-5pp better ratio than zstd-19/lzma but at 40-100x LOWER aggregate decode than pz today and ~10x lower than plzip/xz-T. It is a real frontier point ONLY if you accept that nobody ships a 20%-ratio codec at even 20 MB/s parallel decode — true in the strict sense, but plzip at (24.9%, hundreds of MB/s) sits uncomfortably close and Pareto-pressures it. (2) order-1/2 literals intermediate: ratio ~31-31.5% (from 32.2%), decode maybe 2400-3000 MB/s aggregate (literal coder slowdown only) — a modest, safe, defensible nudge of the EXISTING lzseqr point, strictly better than today, no new thesis required. Point (2) is where the realistic value is.
- **Parallel-decode verdict:** PRESERVED — and this is the one claim that is fully and verifiably true, the family's saving grace. CM/PPM is bit/symbol-serial WITHIN a block but the model is reset per block, so blocks are independent. Verified end-to-end in source: decompress_parallel (parallel.rs:371-393) already spawns one thread per block and calls decompress_block; a Pipeline::Cm codec inherits this with zero scheduler work. ZPAQ is the external existence proof (manpage confirmed: 'blocks decompressed independently in parallel,' level-5 included, at 16x-block-size memory/thread). BUT three skeptical caveats the proposal soft-pedals: (a) parallelism is bounded by core count, so the aggregate number is ~18x a per-core rate that is itself 0.3-2 MB/s — the multiplier is large but the base is so tiny that aggregate still lands at only ~13-36 MB/s, i.e. 40-100x below pz's current decode; (b) per-block model reset is the direct ratio tax, and the cited 18.5% ratios do NOT include it, so 'parallel decode' and 'best ratio' are in direct tension at libpz's 1 MiB granularity — you cannot have both maximally; (c) memory: 16x block per thread for ZPAQ-m5-class means ~288 MiB decode-side state at 1 MiB x 18 threads, manageable but not free. Net: block-parallel decode is genuinely preserved (unlike ParlZ which destroyed ratio, or GPU paths which are dead), but it multiplies a per-core rate so low that the aggregate is still 1-2 orders of magnitude under the rest of pz, and it actively trades against the headline ratio.
- **Dead-end collisions:** No HARD collision: every documented dead-end is GPU-specific (GPU entropy 0.5-0.8x, GPU match-finding atomics-lose-recency, GPU Huffman bit-vs-byte) or rANS-SIMD-specific (SSE2 32% slower). CM/PPM is a pure-CPU, bit/symbol-serial scalar codec, so none of those apply directly. SOFT collision with the M5 entropy-decode wall: the dead-ends establish that per-core entropy decode on this exact CPU is latency-bound and has NO SIMD/GPU rescue (4-way rANS interleave buys only 1.15x; SSE2 is slower; GPU is dead). CM/PPM decode is a STRICTLY HARDER version of the same latency-bound serial dependency (per-bit predict->code->model-update with RMW hash-table thrash). So the same physics that caps rANS at ~432 MB/s/core caps CM at ~0.3-2 MB/s/core, with no escape hatch — this family lives or dies entirely on outer block parallelism, exactly as the dead-ends imply. SOFT collision with 'CPU Recoil via thread::scope is 60x too slow (thread-spawn overhead)': CM must NOT try per-decode threading for the same reason. The proposal correctly rides the existing block scheduler instead, which already amortizes thread spawn across 1 MiB blocks (decompress_parallel spawns one thread per block, not per symbol). Compatible, but only if intra-block parallelism is never attempted. Adjacent to the ParlZ/greedy dead-ends only thematically (ratio-vs-parallelism tradeoffs); no direct conflict since CM doesn't parse LZ.
- **Vet rationale:** Verdict marginal, not reject and not promising, for a sharply split reason. The PROPOSAL'S OWN THESIS-FIT IS REAL: this is the only researched family that genuinely preserves libpz's block-parallel decode (verified in parallel.rs/blocks.rs — a Pipeline::Cm variant inherits it for free, the wire format is additive, and unlike every GPU dead-end this is a clean pure-CPU scalar codec that collides with NO documented dead-end). And the ratio ceiling is the highest of any family: zpaq-m5 18.5% / mcm 18.9% / ppmd-o16 22.2% Silesia are all real, authoritative numbers, far past pz's 32.2% and zstd-19's 24.9%. The CM/PPM-on-binary angle (sao 73.8%, x-ray 54.9%) is also legitimately the right tool where BWT+zrle fall back. THE KILLER is the per-core decode wall, and the verified numbers are worse than the proposal claims: ppmd-J1 1.12 MB/s/core (weak config), ppmonstr 0.28 MB/s/core (strong-ratio config), mcm 1.7-2.9 MB/s/core, lpaq-class ~0.3-1 MB/s/core — so PPMd's '5-15 MB/s/core' estimate is 5-15x optimistic and aggregate decode lands at only ~13-36 MB/s on 18 cores, 40-100x below pz's current 3690 MB/s and ~10x below the plzip/xz-T frontier the thesis wrongly treats as nonexistent. Combined with (a) an unquantified 1 MiB block-reset ratio penalty that could erase 2-5pp of the headline, (b) a from-scratch carry-safe binary range coder + fixed-point mixer as a large, silent-corruption-prone engineering bet (libpz already shipped two silent bbw corruption bugs), and (c) a real risk of becoming a slow, rarely-winning removal candidate like LzssR — the full CM/PPM pipeline is a research-grade bet whose Pareto corner is narrow and conditional on high core count. RECOMMENDATION: do NOT greenlight the full CM pipeline. Pursue ONLY the proposal's Spike A — the binary range coder + order-1/2 model wired to the existing LzSeq literals stream behind a flag. That de-risks the one new primitive with full round-trip fuzzing, banks a safe ~+0.5-1.5pp text win at near-current decode speed without touching the thesis, and yields the data (real range-coder decode MB/s on this CPU) needed to decide whether the full CM bet is ever worth it. Treat Spike B as gated on Spike A AND on a standalone 1 MiB-block CM measurement proving Silesia <=23% AND aggregate decode >=30 MB/s AND a clear win on sao/x-ray — three gates the verified per-core numbers make unlikely to all pass.
### Repeat-offset-aware optimal parsing (cheapest near-term lever) — **MARGINAL** (cost: large, confidence: high)
_Threading true rep-offset state through the parse is a real but modest and binary-skewed lever (~0.1pp text, ~1-2pp binary); for libpz it is dominated by three prerequisites that must land first — widening the parser to u32/1 MiB offsets, fixing the cost model to use real stream entropy, and a btultra2-style two-pass statistics feedback loop — and the empirically larger near-term win is simply that the shipped lazy parser already loses 1.7-2.8pp to plain greedy._
- **Expected Pareto position:** As a standalone rep-state feature: moves the Pareto frontier ~0pp on the Silesia headline (text-dominated) and is gated to an opt-in --quality/-O tier that almost no one runs, so it is essentially Pareto-invisible. As the capstone of the FULL optimal-parse program (un-alias -O + u32 widen + real-entropy cost model + btultra2-style two-pass statistics feedback + rep-state), the whole program lands roughly at zstd-btultra ratio: reymont lazy 30.6% -> high-20s (zstd-9 25.2%, lzma ~24%), i.e. closes most of the gap to zstd-9 but does NOT reach lzma, at 5-15 MB/s/core encode (vs lazy ~50, a 3-10x slowdown). That worsens pz's already-losing compress axis (already 6-9x behind zstd per-core) for an opt-in tier, while decode stays at the measured ~432 MB/s/core (single-thread) / ~7 GB/s aggregate. Net: a high-ratio + parallel-decode point that fits the thesis, but reached mostly by window/stats-feedback, with rep-state contributing the smallest slice.
- **Parallel-decode verdict:** FULLY PRESERVED — this is the family's one unambiguous strength and it survives skeptical scrutiny. Verified in code, not hand-waved: (1) the LzSeq 6-stream wire format is byte-identical regardless of how matches are chosen (lz_token.rs LzSeqEncoder just serializes whatever LzTokens it gets); (2) RepeatOffsets is reset to [1,1,1] at the start of every encode (lzseq/mod.rs:255, encode_from_tokens:673) and reconstructed by the decoder from the offset_codes stream WITHIN each block — no cross-block dependency; (3) the V2 container decodes blocks independently across all cores. A rep-aware parser introduces NO decode-side serial dependency, adds NO new tables, and changes NO bit-alignment. This is the exact contrast with lzma/brotli-11/PPMd (all single-threaded decode) that defines libpz's defensible corner. The only honest caveat: this property is the SAME one every LzSeq parse variant (greedy/lazy/optimal) already has — rep-aware optimal parsing does not ADD parallel-decode capability, it just doesn't destroy it. So on the thesis axis it scores 'preserves' (good) not 'extends' (great); the thesis is satisfied by the encoder family already, and this candidate inherits it for free.
- **Dead-end collisions:** Fully-parallel GPU LZ parse (ParlZ, 37.6% ratio loss): NOT in conflict — this is CPU serial parsing, the explicitly-blessed 'hybrid GPU match-find + CPU serial parse' architecture. Match table can still come from GPU top-K (already wired in tokenize() at pipeline/mod.rs:928). 'Ratio is part encoding, part parse/window' dead-end: ALIGNED, not in conflict. CLAUDE.md already retired the old 'encoding-is-everything' framing and named parse-side as the bigger remaining lever. This family is squarely parse-side. The stale gpu-strategy.md:40 'gap is primarily about match encoding' note is the OLD framing the dead-ends doc corrects. Greedy-as-default regression on structured/record data: PARTIAL conflict / important caveat. The lazy<greedy gap (~3pp text, confirmed in lzseq/mod.rs:878-881) is the cheap win the reviewer correctly flags as dominant, but greedy is NOT a free swap — it regresses nci/record data, which is exactly why lazy is the default. So 'just ship greedy' is itself blocked; the real near-term work is making lazy>=greedy, an open follow-up independent of rep-state. No GPU-entropy / GPU-Huffman / GPU-hash-table conflict: this is pure encode-side match selection on CPU, touches none of those.
- **Vet rationale:** Verdict: MARGINAL. The review is unusually honest and its mechanism claims check out against source: wire format unchanged, block-parallel decode fully preserved (thesis satisfied), -O currently aliases lazy (confirmed in demux.rs:201-209 and pz.rs help text), lazy<greedy ~3pp on text (confirmed verbatim in lzseq/mod.rs:878-881), and the cbloom rep-state numbers reproduce exactly (enwik8 ~0.1%, Fez .pak ~2.7%). Two corrections sharpen the picture against the reviewer's own framing: (a) the MatchTable is ALREADY u32 and the finder ALREADY takes the window — only the final emit truncates — so the 'parser cannot represent the window' framing is too strong; the blocker is the emit + the demux alias, both small. (b) Conversely, the rep-state-CORRECT parser is a FORWARD DP with per-cell rep (zstd opt[cur].rep, confirmed), which libpz's BACKWARD single-best DP cannot do without a rewrite; the cheap path only reuses the existing approximate refinement pass, so the incremental rep gain over what libpz ALREADY ships is below even the literature's 0.1% text figure. The decisive reason this is marginal rather than promising: on the thesis axis, rep-aware optimal parsing does not EXTEND parallel decode — every LzSeq parse variant already has it — it merely doesn't break it, so it buys no new defensible position. And on ratio, rep-state's payoff is ~0 on the text-heavy headline corpus and uncertain on libpz's worst files (sao/x-ray are low-match-density numeric data where rep codes have almost nothing to attach to). The genuinely valuable near-term levers the review surfaces are NOT rep-state: they are (1) make lazy>=greedy (recover ~3pp, but blocked by greedy's structured-data regression), (2) un-alias -O with a u32 emit + real-entropy cost model (optimal.rs:199 flat 4-bit pricing is the true ceiling), and (3) a btultra2-style two-pass statistics feedback loop (no infra exists today; cbloom's 'most important problem in LZ compression', confirmed). Rep-state-in-the-DP is correctly the LAST and SMALLEST step of that program. Recommendation: pursue the parse program in the review's stated order (widen/un-alias -> cost model -> two-pass stats), treat rep-state as a near-zero-cost finishing touch riding the existing refinement pass, and do NOT bill rep-state as a Pareto move on its own. Separately, the worst-file opportunity (sao/x-ray) is better served by a numeric/delta-decorrelation transform than by any LZ parse change.
### Parallel/segment-parallel entropy decode (the thesis vehicle) — **MARGINAL** (cost: medium, confidence: high)
_On the M5 the realistic parallel-entropy win is NOT SIMD-within-block or thread-per-split Recoil (both proven dead here) but MORE independent scalar decode streams per block, Oodle-6-stream style — independent dependency chains that the wide M5 out-of-order core overlaps for free, multiplying pz's existing block-parallel decode advantage at near-zero ratio cost._
- **Expected Pareto position:** Ratio: unchanged by construction (within +/-0.1pp of today — Silesia blob 32.2%, between zstd-3 31.2% and zstd-1 34.6%; literally zero help on the worst files sao 73.8% / x-ray 54.9%, which are an order-0/context-modeling problem). Speed: the realistic, defensible delta is a one-line Lzf->4-way-FSE routing giving ~1.15x single-thread (lzf ~432->~497 MB/s ST; ~7% aggregate), ratio-neutral, near-zero cost. That still leaves pz ~3x behind zstd-3 per core (1513 MB/s) — it does NOT move pz onto the single-thread Pareto frontier, and it only widens an aggregate-decode lead pz already holds. The ambitious N=6/8 FSE-substream stage is projected by prior art to land at or below the 4-way point on this hardware, i.e. it could REGRESS (8-way scalar rANS was slower in every published scalar benchmark). Net Pareto movement: negligible-to-slightly-positive on the speed axis pz already leads, nothing on the ratio axis where pz actually needs help.
- **Parallel-decode verdict:** It does preserve block/segment-parallel decode — that part is not in question, because the cross-core layer (decompress_stream_parallel, ~13x scaling, 2700-3700 MB/s aggregate) is already shipped and entirely orthogonal to this change; nothing here serializes or threatens it. But that is also why the thesis value is thin: the parallel-decode moat ALREADY EXISTS and is realized via block parallelism, so this family adds a SECOND, within-block ILP axis whose measured payoff on the M5 is only 1.15x (FSE) and is negative for scalar rANS beyond 4-way. The crucial skeptical point: the proposal's framing that within-block N-stream ILP 'multiplies' the block-parallel advantage is not borne out — the two axes do not multiply once cores are saturated and bandwidth-bound, and the per-stream chain the M5 OoO core already overlaps for free leaves almost nothing for explicit interleaving to harvest. So: parallel-decode-safe, yes; parallel-decode-thesis-advancing, no. It defends the existing corner rather than extending it.
- **Dead-end collisions:** Directly collides with the freshest M5 measurement (MEMORY.md / libpz-pareto-progress, 2026-06-09): '4-way interleaving only gives 1.15x on FSE decode in isolation (367->422 MB/s)... The M5's wide OoO engine already hides most single-stream latency, so interleaving's latency-hiding barely helps here.' The proposal's central premise (wide M5 core overlaps N chains 'for free, multiplying the win') is the inverse of what was measured: a core that already hides single-stream latency has LESS to gain from more streams, not more. Collides with the Recoil tar-pit dead-end (docs/design-docs/gpu-recoil-findings.md): sequential Recoil = 3.1x SLOWER than plain interleaved (86 vs 268 MB/s, per-split restart cost), thread::scope Recoil = 60x slower (88 vs 5606 MB/s). The proposal acknowledges this but still leans on Recoil as a 'partitioner' — a role for which there is zero measured upside on libpz's already-shipped block-parallel layer. Collides with the standing 'per-core entropy decode is near a hardware wall' conclusion and the explicit MEMORY bottom-line: 'There is NO cheap per-core decode win on typical data... the only realistic path to single-thread parity is a zstd-class entropy decoder rewrite (large, risky).' The SSE2/NEON-rANS dead-end (SSE2 32% slower than scalar; NEON path is a scalar stub with no gather) is correctly avoided by the proposal (it stays scalar) — so no NEW collision there, but it is the same root cause (no fast gather on the M5) that caps the scalar-N approach too.
- **Vet rationale:** This family is correctly identified as ratio-neutral and parallel-decode-safe, but the entire pitch is a SPEED bet, and that bet was already run on the exact target hardware one day before this review: libpz's own 2026-06-09 M5 measurement (MEMORY.md / libpz-pareto-progress) shows 4-way FSE interleave = 1.15x, ratio-neutral, with the explicit finding that 'the M5's wide OoO engine already hides most single-stream latency, so interleaving's latency-hiding barely helps.' That is the inverse of the proposal's premise. The external prior art the proposal leans on splits cleanly: the strong 1.52x result is Oodle 6-stream HUFFMAN (a short shift+table critical path that scales), while jkbonfield's actual scalar rANS benchmarks show 8/16/32-way DEGRADE decode and only SIMD recovers higher-N — and Giesen's papers attribute the scalar plateau to gather/table-lookup latency, the same no-fast-gather root cause that already killed SSE2/NEON rANS here. FSE/tANS sits on the rANS side of that divide, so the proposal's highest-value 'new stage' (an N=6 FSE decoder) is the least-supported piece and is projected to land at or below today's 4-way point. There is exactly one defensible, free win embedded in all this: the Lzf default path genuinely still uses single-state fse::decode (blocks.rs:218 -> stages.rs:693), while the 4-way fse_decode_interleaved already exists and is wired for LzSeqR; routing Lzf to it is a one-line, ratio-neutral ~1.15x (~7% aggregate) change requiring NO new code, NO new wire format, and NO Recoil. That is worth doing as cleanup — but it is a marginal tidy-up of an axis pz already leads, not the thesis vehicle. The thesis needs a per-core entropy decoder competitive with zstd's huff0+BMI2 (a ground-up rewrite, large/risky) or a RATIO lever (BWT speed, order-1, the worst-file modeling problem) — and this family delivers neither. Verdict: marginal. Do the one-line Lzf 4-way routing; do NOT build the N=6/8 FSE substream stage or any Recoil-driven decode on the strength of the Oodle-Huffman analogy; do NOT spend the recommended 8-way-rANS spike expecting >=1.3x — the closest published number says it will be slower, and the M5's own 1.15x says the headroom isn't there.
