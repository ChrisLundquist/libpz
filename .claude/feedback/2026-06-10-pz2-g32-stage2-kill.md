# pz2-G32 stage 2: GPU decode killed with data — CLAUDE.md dead-ends update

The "GPU entropy is slower than CPU" dead-end entry needs an amendment, in both directions:

1. **The old entry's mechanism was wrong but its conclusion survives.** The 0.54x GPU
   decode result was a serial-state topology artifact (~300-640 states). With the wire
   designed for the GPU (32-lane lane-pinned Huffman, pz2-G32), a Metal kernel decodes
   the literal phase at **64.75 GB/s** on M5 Max — GPU entropy decode is NOT slow.
2. **What actually kills GPU block decode on this hardware is the splice + unified
   memory.** End-to-end (literal kernel + cooperative splice) = 3.92 GB/s vs CPU
   all-cores 18.28 GB/s = **0.21x**. The splice is 53.4 of 54.0 ms; even with free
   sequence-entropy the copy loop alone is 2.9x slower than the entire CPU decode.
   The in-block LZ copy chain caps parallelism at block count (106), and 18 CPU cores
   sharing the same ~0.5 TB/s already saturate the real bottleneck.

Suggested dead-end entry: "GPU block decode of LZ formats is dead on unified-memory
Apple silicon — not because of entropy (a wire-codesigned Metal kernel hits 65 GB/s on
literals) but because the LZ splice has only block-level parallelism and the CPU shares
the same memory bandwidth. Measured end-to-end 0.21x CPU all-cores (pz2-G32 stage 2,
2026-06-10). Generalizes to all decode-side GPU candidates (dietpz, num-G, gpu-ibwt,
pz2-GA). Reopen only for discrete-GPU persistent-process embeddings or GPU-resident
output pipelines. See docs/design-docs/pz2-g32-stage2-findings.md."

Also: the 32-lane wire is NOT a CPU win (NEON 0.55-0.61x the shipped 8-lane layout
ST) — nobody should "graduate" the G32 transcoder to the container on CPU grounds.
