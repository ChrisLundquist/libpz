# pz2-G32 stage 2: GPU decode killed with data — CLAUDE.md dead-ends update

The "GPU entropy is slower than CPU" dead-end entry needs an amendment, in both directions:

1. **The old entry's mechanism was wrong but its conclusion survives.** The 0.54x GPU
   decode result was a serial-state topology artifact (~300-640 states). With the wire
   designed for the GPU (32-lane lane-pinned Huffman, pz2-G32), a Metal kernel decodes
   the literal phase at **64.75 GB/s** on M5 Max — GPU entropy decode is NOT slow.
2. **What kills GPU block decode on this hardware is the LZ splice + the shared
   memory system.** End-to-end (literal kernel + cooperative splice) = 3.92 GB/s vs
   CPU all-cores 18.28 GB/s = **0.21x** at the real operating point (one corpus in
   flight: 106 threadgroups, ~5% occupancy, latency-bound on each block's serial
   chain). Saturating occupancy with 16 concurrent corpus copies (`--dup 16`,
   3.4 GB in flight) lifts the GPU only to **parity (1.02x, spreads 10-16%)** —
   both engines converge on the same ~20 GB/s shared-memory ceiling, so the GPU
   never wins wall-clock at any occupancy.

Suggested dead-end entry: "GPU block decode of LZ formats is dead on unified-memory
Apple silicon — not because of entropy (a wire-codesigned Metal kernel hits 65 GB/s on
literals) but because the splice is latency-bound at real occupancy (0.21x CPU
all-cores, one stream in flight) and plateaus at CPU parity (~20 GB/s, 1.02x) even at
16x synthetic saturation — the shared memory system is the common ceiling. Measured
end-to-end, pz2-G32 stage 2, 2026-06-10. The only residual is core-offload-at-parity
for a persistent process decoding many concurrent streams (a product hypothesis, not a
perf win). Reopen only for that, discrete-GPU machines, or GPU-resident-output
pipelines. See docs/design-docs/pz2-g32-stage2-findings.md."

Also: the 32-lane wire is NOT a CPU win (NEON 0.55-0.61x the shipped 8-lane layout
ST) — nobody should "graduate" the G32 transcoder to the container on CPU grounds.
